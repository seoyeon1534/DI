# @report

## 목적

앞 단계들의 작업을 **임원이 5분에 읽을 수 있게 압축한다.**
"무엇을 발견했는가" 보다 "무엇을 해야 하는가" 가 중심이다.

**이 단계는 감사하지 않는다.** 대시보드와 수치의 검증은 `/audit-analysis`가 한다.
같은 파이프라인의 마지막 단계가 상류를 채점하면, 요약하려는 동기가 흠을 찾으려는
동기를 이긴다. 역할을 나눠 둔 이유다.

## 인풋

1. `runs/latest/input/00_context.md` — **누가 읽는가, 어떤 결정을 앞두고 있는가**
2. `runs/latest/outputs/03_problem_definition.md`
3. `runs/latest/outputs/04_kpi_summary.md`
4. `runs/latest/outputs/05_analysis_report.md`

## 작업

### 1. 독자 확인

`00_context.md` 의 "누가 이 분석을 필요로 하는가" 를 읽고 보고서의 눈높이를 정한다.
독자가 명시되지 않았으면 임원 기준으로 쓰고 그 가정을 첫 줄에 밝힌다.

### 2. 압축

**새로운 발견을 추가하지 않는다.** 05에 없는 수치를 만들지 않는다.
05의 인사이트 3개를 각각 3~4줄로 줄인다. 무엇을 버릴지가 이 단계의 판단이다.

버리는 기준: 앞둔 결정에 영향을 주지 않는 것은 버린다.

### 3. 판단 표시

각 지표에 상태를 붙인다 — 양호 / 경고 / 위험.
기준은 04의 비교 기준을 쓴다. 새 기준을 만들지 않는다.
표본이 부족한 지표에는 판단 대신 "표본 부족" 을 적는다.

### 4. 액션 플랜

05의 P1/P2/P3를 그대로 가져오되, 각 액션에 **기대 효과**와 **기한**을 붙인다.
`00_context.md` 의 제약에 걸리는 것은 제외하거나 제약을 명시한다.

### 5. 남은 불확실성

05의 "이 결론이 틀렸다면" 을 모아 한 절로 옮긴다.
임원이 이 보고서로 결정할 때 무엇을 감수하는지 알아야 한다.

**이 절을 빼지 않는다.** 확실해 보이는 보고서가 확실한 보고서는 아니다.

### 6. 저장

`runs/latest/outputs/07_executive_report.md`

## 출력 형식

```markdown
# Executive Report

## 한 줄 요약
[공유할 수 있는 한 문장]

## 앞둔 결정
[00_context.md 의 결정] — 이 보고서는 그 결정에 이렇게 답한다: [한 줄]

## 분석 배경
- 데이터: [파일명 / 기간 / 행 수 / 집계 단위]
- 핵심 질문:

## 핵심 지표
| 지표 | 현재값 | 비교 기준 | 판단 |
| … | … | … | 양호 / 경고 / 위험 / 표본 부족 |

## 주요 발견 (3개)
1. [발견] — 근거: [수치] — 결정에의 영향: [무엇을 바꾸는가]

## 액션 플랜
| 우선순위 | 액션 | 기대 효과 | 기한 |
| P1 즉시 | | | |
| P2 단기 | | | 2~4주 |
| P3 모니터링 | 지표 / 기준 / 주기 | | 상시 |

## 남은 불확실성
- [이 결론이 틀릴 수 있는 지점과 무엇을 보면 알 수 있는가]

## 산출물
- 대시보드: runs/latest/outputs/06_dashboard.html
- 상세 분석: runs/latest/outputs/05_analysis_report.md
- 지표 정의: runs/latest/outputs/04_kpi_summary.md
- 검증: /audit-analysis 실행 결과 참조
```

## 원칙

- 임원은 맥락을 모른다 — 자기완결적으로 쓴다
- 발견이 아니라 결정으로 끝난다
- 수치에는 단위와 기준을 항상 붙인다
- 05에 없는 수치를 만들지 않는다
- 불확실성을 지우지 않는다

## 하지 않을 것

- 새로운 분석·새로운 수치
- 대시보드 품질 감사 (`/audit-analysis`의 일)
- 지표 판단 기준을 새로 만드는 것
- "남은 불확실성" 절을 비우는 것
