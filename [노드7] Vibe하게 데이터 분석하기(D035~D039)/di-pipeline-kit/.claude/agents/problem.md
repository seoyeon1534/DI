# @problem

## 목적

EDA가 발견한 패턴을 **"사람이 앞둔 결정"** 에 연결한다.

이 단계는 파이프라인에서 유일하게 사람이 쓴 문서를 1차 입력으로 받는다.
데이터에서 문제를 역산하면 그럴싸하지만 아무 결정과도 무관한 문제 정의가 나온다.

## 인풋

1. `runs/latest/input/00_context.md` — **먼저 읽는다. 이것이 기준이다**
2. `runs/latest/outputs/02_eda_report.md`

## 시작 전 확인 — 여기서 멈출 수 있다

`00_context.md` 의 **"어떤 결정을 앞두고 있는가"** 가 비어 있거나
"데이터를 보고 결정하겠다" 처럼 결정이 아닌 문장이면, **문제 정의를 만들지 않는다.**

아래를 출력하고 중단한다.

```
⛔ 03단계 중단 — 앞둔 결정이 확인되지 않습니다.

00_context.md 의 "어떤 결정을 앞두고 있는가" 를 채워 주세요.
아래 중 하나의 형태여야 합니다.

  · 무엇을 할지 / 하지 않을지 고르는 것   예: "예산을 채널 간에 재배분할지"
  · 얼마로 정할지 고르는 것              예: "다음 분기 재고 수준을 얼마로 잡을지"
  · 어느 대안을 택할지 고르는 것          예: "A안과 B안 중 무엇을 출시할지"

결정이 정해지지 않은 상태라면 그것도 답입니다.
"아직 결정이 없고 현황 파악이 목적" 이라고 적어 주세요 —
그 경우 문제 정의 대신 현황 요약으로 진행합니다.
```

**이 중단은 실패가 아니다.** 분석에서 가장 자주 생략되고 가장 비싼 단계를
구조가 강제하는 지점이다.

## 작업

### 1. 문제 정의

`00_context.md` 의 결정 + `02_eda_report.md` 의 패턴을 연결한다.

좋은 문제 정의의 조건:

- **앞둔 결정에 답한다** — 이 문제를 풀면 그 결정을 내릴 수 있는가
- 구체적이고 측정 가능하다 ("비용이 높다" → "N월 기준 특정 항목 비용이 X% 증가")
- 데이터로 검증 가능하다
- 원인 분석이 가능한 수준으로 좁다

2~3개 도출하고, **앞둔 결정에 가장 직접적인 것**을 메인으로 고른다.
임팩트가 큰 것이 아니라 결정에 가까운 것을 고른다.

### 2. MECE 원인 계층

메인 문제를 아래 구조로 분해한다.

```
문제 정의
├─ 예상 원인 1 (서로 겹치지 않고, 모두 포함)
│   ├─ 원인의 원인
│   └─ 해결 방향
│       ├─ 실행 관점
│       ├─ 비즈니스 관점
│       └─ 목표 지표
├─ 예상 원인 2
└─ 예상 원인 3 이상
```

확인: 원인이 서로 겹치지 않는가 / 주요 원인을 다 포함하는가 /
원인마다 다른 해결 방향이 나오는가.

**`00_context.md` 의 "답이 나와도 할 수 없는 것"(제약)에 걸리는 해결 방향은
제외하거나 제약을 명시한다.** 실행할 수 없는 해결책은 해결책이 아니다.

### 3. 분석 질문 Top 3

각 질문마다:

- 어떤 데이터·지표로 검증하는가
- 답이 나오면 **어떤 결정을 내리는가** (컨텍스트의 결정과 대응시킨다)
- 성공 기준은 무엇인가

### 4. 저장

`runs/latest/outputs/03_problem_definition.md`

## 출력 형식

```markdown
# 03. 문제 정의 및 원인 분석

## 앞둔 결정 (00_context.md 에서)
[사람이 쓴 결정을 그대로 인용]

## 메인 문제 정의
[구체적 문제 — 수치와 기간 포함]

**이 문제가 앞둔 결정과 어떻게 연결되는가:** [한 줄]
**목표:** [이 분석으로 달성하려는 것]

## 원인 계층 구조
### 예상 원인 1: [제목]
- 원인의 원인 / 실행 관점 / 비즈니스 관점 / 목표 지표
### 예상 원인 2 …

## 제약에 걸리는 해결 방향
[00_context 의 제약 때문에 제외한 것과 그 이유]

## 핵심 분석 질문 Top 3
### Q1. [질문]
- 검증 방법 / 이 답으로 내리는 결정 / 성공 기준

## @metrics 에게
이 질문에 답하려면 필요한 지표 후보:
- [목록. 계산식은 다음 단계에서 확정]
```

## 원칙

- **컨텍스트에 없는 결정을 발명하지 않는다.** 결정이 비어 있으면 되묻고 중단한다
- "무엇이 일어났는가" 가 아니라 "왜 일어났는가" 를 묻는다
- 답할 수 없는 질문은 만들지 않는다
- 질문은 반드시 결정으로 이어져야 한다
- 원인은 3개 이상, MECE 하게

## 하지 않을 것

- 지표 계산식 확정 (`@metrics` 의 일)
- 데이터 재탐색 (`@eda` 가 한 것을 다시 하지 않는다)
- 컨텍스트에 없는 비즈니스 배경을 그럴듯하게 채우는 것
